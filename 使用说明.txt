会话监控工具（Codex + Pi） — 使用说明（Windows + Mac）
========================================================

【目录结构】
  Windows/  Windows 版（exe，免装 Python）—— 整个文件夹一起复制，别只拷 exe
    codex_monitor_gui.exe  主程序（Codex + Pi 统一控制台），双击运行
    codex_monitor.exe      Codex 监控子进程（必须和 gui.exe 同目录，不要单独运行）
    pi_monitor.exe         Pi 监控子进程（同上）
    _gui/ _codex/ _pi/     三个程序各自的运行库目录（各自对应一个 exe，缺了那个程序起不来）
  Mac/      Mac 版（Python 脚本，Mac 自带 python3）
    codex_monitor_gui.py   主程序（Codex + Pi 统一控制台）
    codex_monitor.py       Codex 监控子进程
    pi_monitor.py          Pi 监控子进程
    启动.command            双击启动（首次需先加执行权限，见下）
  Pi插件/    Pi 端插件源码（Pi 的发送通道，必须安装，见第 5 节）
    local.session-keeper/  插件本体（manifest.json + main.js + renderer/）
  install_pi_plugin.py      安装/检查 Pi 插件的脚本（Windows 与 Mac 通用）
  _旧版onefile备份/         上一版（onefile 打包）的三个 exe，仅回退用，可整个删掉
  使用说明.txt

========================================================
【1. 两个来源的差别（先看这一节）】

  Codex：有命令行入口，监控脚本直接调用
         codex queue --thread <会话ID> --message "继续"
         来发送，装好就能用。

  Pi（PI-Desktop）：没有任何命令行入口。
         Pi 的 host-core 只接受它自己 Electron 主进程的 stdio 握手，
         外部脚本无法直接给会话投递消息（这一点和 Codex 根本不同）。
         因此 Pi 的发送走一个官方插件（local.session-keeper），
         插件内部调用 Pi 官方操作 agent/prompt
         （"Send a prompt to a session's Agent"）。

  → 结论：想监控 Pi 会话，必须先装那个插件（见第 5 节）。
    不装的话，Pi 监控会明确报「发送通道不可用」并退出，
    不会静默地什么都不做。

========================================================
【2. 睡觉挂机必读：权限模式必须是「全自动」】

  这是能否无人值守跑通宵的**决定性前提**，请务必先读。

  Pi 的每个会话有一个「权限模式」，决定工具操作要不要问你：
      全自动（auto）          不询问，直接跑  ← 睡觉时唯一安全的选择
      自动接受编辑（accept-edits）  编辑不问，其它高风险操作仍会问
      每次询问（ask）          每次都问
      跟随默认（inherit）      跟随应用默认设置（默认可能是"每次询问"）

  如果会话不是「全自动」：半夜 agent 想改文件/跑命令时会弹确认框，
  它会一直卡在那里等到早上你手动点一下 —— 这恰恰是挂机续跑要解决的问题。
  这种情况下，续跑工具发多少条"继续"都没用。

  【怎么检查 / 怎么修】
    1. 启动监控时会自动检查，非全自动的会话会打印醒目警告并拒绝启动
       （除非你加 --allow-unsafe 明确接受这个风险）
    2. 打开「会话续跑」插件面板 → 会话列表里有一列「权限」，
       绿色=全自动（安全），红色=其它（半夜可能卡住）
    3. 面板里点「把未全自动的会话切到全自动」可批量修正
       （Pi 会对每个会话弹一次原生确认框，这是它的安全设计，插件无法绕过；
        睡前点几次即可，比半夜被卡住强）

  【注意】全自动 = 不询问就运行命令、可能修改文件。请自行评估风险，
         建议只对你信任的、确实需要通宵跑的任务开启。

========================================================
【3. 典型场景：睡前挂机（监控 3 个会话 / 异常续跑 / 全完成关机）】

  这是最常用的场景，完整步骤如下（约 2 分钟）：

  ── 第 1 步：确认会话是「全自动」权限模式 ──
     见上一节。启动监控时会自动检查，不是全自动会拒绝启动并提示。

  ── 第 2 步：打开控制台，选中要监控的 3 个会话 ──
     1. 双击 codex_monitor_gui.exe
     2. 在「会话列表」里找到 [Pi] 开头的项目，点开
     3. 逐个【点击】要监控的会话 —— 点中会打 ✓ 并出现在下方
        「要监控的对话」列表里；点错了再点一次即可移出
     4. 确认下方列表正好是你要的 3 个

     · 不选任何会话 = 自动模式，会按「监控会话数」取最近活跃的 N 个
     · 选了会话 = 只监控这些，不会再自动拉入别的

  ── 第 3 步：勾选「所有会话都『正常完成』后关机」 ──
     位置：「关机规则」区域
     后面的秒数保持 120 即可（全部完成后先观察 2 分钟，防止刚好又有新任务）

     这条规则和「全部停止」的区别（重要）：
       · 「正常完成」= 每个会话最后一个回合都是「已完成」
         → 只有任务真的干完了才关机
       · 卡在等确认、失败、还在跑的会话都【不算】完成
         → 不会出现「活没干完就关机」
       所以这个场景请用「正常完成」，不要用「全部停止」。

     ⚠ 如果你同时监控了 Codex 和 Pi：
       请一并勾上「要求所有监控来源都完成才关机」（默认已勾）。
       不勾的话，先跑完的那个来源会把机器关掉，
       而另一个来源的任务还在跑 —— 那就成了「活没干完就关机」。
       只监控一个来源时，这个勾选项自动失效，不用管它。

  ── 第 4 步：（可选）勾选 Pi 通知 ──
     「Pi 完成/失败/等待确认时弹通知」—— 想睡醒后看过程就勾上。

  ── 第 4b 步：（可选）确认 Pi 报错续接已开 ──
     位置：Pi 插件面板「会话续跑」（推荐：睡前在插件里勾一次就生效），
           或 GUI 的「报错/400 续接（仅 Pi）」区域。
           两处是同一个开关，GUI 打开时会自动跟随插件面板的设置。
     默认已勾选、连续 3 次、模式 compact；另有「真报 400 直接新建会话」默认也开着。
     这是防止半夜某个会话报错（Pi 的 400）/ 上下文爆掉后彻底卡死的保险：
       · compact（默认）= 先压缩上下文，压不动才新建会话续接
       · new           = 直接新建会话续接
     触发后原会话自动停止监控、新会话自动接管，不需要你半夜起来处理。
     ⚠ 判定与执行由监控脚本负责，所以需要 GUI（或 pi_monitor.py）在运行。

  ── 第 5 步：启动 ──
     确认「模拟运行」没勾 → 点「▶ 启动监控」
     日志里应出现这几行才算正常：
      [Pi] 发送通道：执行器正常（插件 v1.9.2…）
       [Pi] 无人值守检查：所有被监控会话都是「全自动」模式 ✓
       [Pi] 监控会话：xxx（3 行，对应你选的 3 个）

  然后就可以去睡了。GUI 可以最小化，但不要关。

  ── 夜里会自动发生什么 ──
     · 某会话异常中断（aborted/error）→ 等 1 分钟后发「继续」
       连续失败则退避 1、1、3、5、5 分钟，成功一轮后清零
     · 会话正常跑完 → 什么都不做，继续等其他会话
     · 某会话上下文超限（CONTEXT_TOO_LARGE）连续 3 次 → 先压缩上下文；
       压不动则新建会话并把任务交接过去，原会话退出、新会话自动接管
     · 某会话真报 HTTP 400（按 Pi 日志里的真实状态码判定）→ 直接新建会话把任务接过去，
       不等连续次数、也不先压缩
     · 3 个会话全部「已完成」→ 观察 120 秒，仍无新活动 → 关机

【4. 基本使用】

  1. 确保要监控的应用已打开并登录（Codex 桌面端 / PI-Desktop）
  2. 进入 Windows 文件夹，双击 codex_monitor_gui.exe
     · 只会有一个控制台：已经开着一个时，再双击不会开出第二个，
       而是把那个窗口拉到前台（两个控制台会各自启动一套监控，同一会话被重复发送）
     · 三个 exe 都在同一个文件夹里，exe 旁边的 _gui / _codex / _pi 是运行库，
       搬动/复制时整个 Windows 文件夹一起走
  3. 首次建议勾选「模拟运行」试跑，确认日志里能看到你的会话
  4. 取消「模拟运行」后正式启动

【Mac 使用】
  1. 确认装了 python3 和 tkinter：
       终端运行 python3 --version，有版本号即可
       如果运行报错 "No module named tkinter"，执行 brew install python-tk
  2. 首次启动：打开「终端」，cd 到 Mac 文件夹，执行：
       chmod +x 启动.command
     以后双击 启动.command 即可
     或者直接在终端运行：python3 codex_monitor_gui.py

【5. 安装 Pi 插件（监控 Pi 会话必做）】

  ── 方式 A（推荐，一步到位）──
  在工具根目录双击/执行：
     local.session-keeper-1.9.2.piplug
  或者：
      1. 打开 PI-Desktop
      2. 点左下角「扩展」（英文界面是 Extensions）
      3. 点右上角「更多操作 ⋯」→「安装插件包」
     4. 选中 local.session-keeper-1.9.2.piplug
  装完会自动启用，并弹出权限确认页 —— 三项全部允许：
      ui.panel（显示插件面板）
      background.service（保持后台服务运行）
      desktop.control（控制桌面操作）← 缺这项就无法发送

  ── 方式 B（源码方式，想自己改代码时用）──
  在工具根目录执行：
      python install_pi_plugin.py
  脚本会把插件复制到 Pi 的插件目录并登记，然后：
      1. 打开 PI-Desktop → 左下角「扩展」
      2. 右上角「更多操作 ⋯」→「加载本地插件」
      3. 选择这个目录：
           Windows: C:\Users\<你的用户名>\.pi-desktop\plugins\installed\local.session-keeper
           Mac:     ~/.pi-desktop/plugins/installed/local.session-keeper
      4. 权限确认页里同样三项全部允许

  ── 找入口的提示 ──
  · 中文界面里这一页叫「扩展」，不是「插件」（图标在左侧栏最下方的设置旁边）
  · 快捷键：Alt+Space 打开「插件启动器」，可快速搜索并打开某个插件的面板
  · 如果「已安装」列表是空的，页面中间会直接显示「加载本地插件」按钮

  ── 验证是否装好 ──
      python install_pi_plugin.py --check
  看到「执行器心跳：正常」就说明通道已通。
  也可以在控制台里看「监控来源」那一行：Pi 后面显示 ✓ 即正常。

  说明：
    - 插件只做「执行器」，自己不判定、不轮询、不决定发送节奏，
      判定与节奏全部由外部监控脚本负责，因此不会出现同一会话被重复发送。
    - 插件面板（Alt+Space 搜「会话续跑」，或命令面板搜同名）里可以看运行状态、
      核对官方操作是否可用、并对某个会话做一次发送自检。
    - 面板顶部的「监控脚本」一行最关键：它显示 Pi / Codex 的监控脚本
      有没有在跑（运行中 / 未运行 / 模拟运行）。
      ⚠ 只装插件、不开监控脚本 = 什么都不会发生：
        插件只是执行器，判定与发送全靠监控脚本。会话报错后没人处理，
        多半就是这一行显示「未运行」。
    - 插件面板的「设置」区里可以直接配置（保存后外部脚本会读到）：
        · 关机策略：所有会话都「正常完成」后关机 / 完成后再观察多少秒 /
          要求所有监控来源都完成才关机（跨来源协调，默认勾选）
        · 报错续接（Pi）：会话连续报错时自动续接 / 连续次数 / 续接方式
          （compact=先压缩上下文、压不动再新建会话；new=直接新建会话）
        · 插件面板的「保存设置」把值写进插件自己的 settings.json（不走 Pi 的设置存储），
          保存后立即刷新心跳，监控脚本下一轮就读到；保存失败会在按钮旁直接显示原因
        · 报 400 直开（Pi）：真报 400 时直接新建会话（不等次数、不压缩）
        · 全 503 关机：近期活跃会话全部报 503 时关机 / 活跃窗口（分钟）
      优先级：监控脚本的命令行参数 > 插件面板设置 > 内置默认。
      也就是说，GUI 里显式勾选的会覆盖插件设置；
      而 GUI 对应的复选框本身就是读插件设置的（默认跟随，避免两个入口打架）。
    - 监控脚本的日志文件在程序所在目录：pi_monitor.log / codex_monitor.log
      （GUI 启动时会显式指定，便于事后排查）。
    - 插件源码就在 Pi插件/local.session-keeper/ 里，可自行审阅。

【6. 界面说明】

  - 监控来源（可分别开关）：
      Codex / Pi 两个复选框。右侧实时显示各自状态：
        Codex → 数据库是否就绪
        Pi    → 插件执行器心跳是否正常
      点「重新检测通道」可手动刷新。

  - 会话列表（按「来源 + 项目」分组，可展开/收起）：
      · 打开窗口后自动列出两个来源的全部未归档会话，组名形如
        [Codex] 项目名 / [Pi] 项目名（项目名带会话数）
      · 默认展开最近活跃的前 3 个项目，其余收起；点项目左侧箭头可展开/收起，
        或点「展开全部 / 收起全部」
      · 每个会话显示：会话名、最后活动时间、状态
        （进行中 / 已完成 / 已失败 / 已停止 / 已停止(残留)）
      · 「已停止(残留)」= Codex 被中断时留下的 inProgress 记录：它不会自己改成
        interrupted，所以几天前的会话会一直显示「进行中」。判定标准是 15 分钟内
        没有任何活动（看该会话的 rollout 文件）。这种残留不会被自动发「继续」，
        也不会让「全部完成」关机触发（想按「没活动就关机」请开「全部停止 N 分钟」）
      · 【已归档 / 已删除的会话不显示】删除按数据库的 deleted_at 判定；
        归档是 PI-Desktop 界面上的状态，它不在 pi.sqlite 里（存在 PI-Desktop 的
        Local Storage），监控会去读那份表并跳过。列表底部写明「已屏蔽归档 N 个」；
        读不到那份表时会显示「未屏蔽归档」并照常列出（宁可多列，不乱屏蔽）

  - 要监控的对话（下方）：
      · 在左侧会话列表上【点击某个会话】即加入下方监控列表（会打上 ✓ 标记）；
        再次点击同一会话可移出；可多选
      · 也可在下方列表选中后点「移除选中」，或「清空」
      · 启动后只监控下方列表里的会话（不会再自动拉入其他会话）
      · 下方列表为空 = 自动模式：两个来源各自按「监控会话数」自动选最近活跃的 N 个
      · 会话有变化（如新建/归档）点「刷新列表」重新加载（归档后该会话会从列表消失）

  - 监控范围（三种，选一种）：
      1) 勾选具体会话（推荐，最可控）：
         在会话列表里点选，只有被选中的会被监控。
      2) 自动取最近活跃 N 个：
         不选任何会话时，两个来源各自按「监控会话数」取最近活跃的 N 个。
      3) 监控所有活跃会话（命令行 --active-within N）：
         把「最近 N 分钟内有活动」的全部会话都纳入监控，
         且之后新出现的活跃会话会自动加入（包括自动续接新开出来的会话）。
         ⚠ 为什么不直接「监控全部会话」：
           实测 307 个未归档会话里有 58 个最后状态是 error/aborted，
           但其中只有 2 个是最近真出问题的，其余是几天前到一个月前的历史遗留。
           直接监控全部会一次性误触发 56 个旧会话、狂开新会话、烧掉大量 token。
           用时间窗口就天然避开了这个问题。
         建议窗口：60 分钟（睡前挂机够用；漏掉的会被下次启动补上）。

  - 基础参数：监控会话数（默认 2，仅在不选会话时生效）、轮询间隔、发送消息（默认"继续"）、
    退避节奏 1,1,3,5,5 分钟（连续失败第1、2次等1分钟，第3次等3分钟，第4次起等5分钟，每次±3秒随机）、
    ±随机抖动、每小时发送上限、发送后重试间隔

  - 关机规则（四个独立开关，默认都不勾选）：
      · 错误码连续 N 次后关机（默认 3 次）
          Codex 按 HTTP 码判断（405、503）
          Pi 按 turns.error_code 判断（STREAM_FAILED、PROVIDER_ERROR）
      · 全部停止 N 分钟后关机（默认 20 分钟）
      · 所有会话都「正常完成」后关机（Codex 和 Pi 都支持）
          判定口径：每个会话最后一个回合都是「已完成」。
          卡在等确认、失败、还在跑的会话都【不算】完成，
          所以不会出现「活没干完就关机」。全部完成后先观察 N 秒
          （默认 120）再关，防止刚好又有新任务进来。
          这条比「全部停止」精确，睡前挂机推荐用它。
      · 近期活跃会话「全部报 503」后关机（默认不勾选）
          与「错误码连续 N 次」互补：服务商整体挂掉时，每个会话各报一次 503，
          单会话计数永远到不了阈值，只有这条能触发。
          判定口径：所有「近期活跃」（活跃窗口内有活动，默认 60 分钟）的
          被监控会话，最后一个回合都是 503 → 直接关机。
          更早的历史会话不参与判定（否则几天前的旧错误会让规则永远不成立）。
          窗口可调；一个近期活跃会话都没有时【绝不关机】。
          判定依据（两边都是精确匹配，不是猜的）：
            Codex：错误 JSON 里的 HTTP 状态码，命中 503 才算
            Pi：turns.error_code 区分不了 400 和 503（都记成 PROVIDER_ERROR），
                所以读 Pi 自己的日志 ~/.pi-desktop/logs/app/session*.log 里的
                agent.turn.failed 事件 —— 它的 data.message 前缀就是真实状态码
                （如 "503: {...}"、"400: {...}"），据此只认 503。
                日志里查不到的会话按「不是 503」处理：宁可漏触发，也不凭猜测关机。

                另外还要求日志时间与该会话最后一个回合对得上（容差 5 分钟）：
                会话早已恢复正常时，它几小时前留下的旧 503 记录不会被算数，
                避免拿过期记录把机器关掉。
      · 关机指令已按平台自动适配
          可以填自定义指令（如调用脚本）；执行失败会在日志里明确报
          「未关机」，不会假装成功。

  - 跨来源关机协调（同时监控 Codex 和 Pi 时重要）：
      · 背景：Codex 和 Pi 是两个独立进程，各自只看得到自己那部分会话。
        如果各自判定「我这边全完成了」就关机，那么先跑完的那个
        就会把机器关掉 —— 而另一个来源的任务还在跑。
      · 「要求所有监控来源都完成才关机」（默认勾选）：
          两个进程通过一个共享文件互相登记完成状态，
          只有两边都登记完成才真正关机。
          协调文件位置：~/.session-monitor/shutdown-coord.json
      · 不勾选时：各自独立判定，谁先完成谁关机（旧的简单行为）
      · 只监控一个来源时，这个选项自动失效（否则永远等不到对方，就不会关机了）
      · 安全兜底：若某个来源的登记超过 10 分钟没刷新（说明那个进程已退出），
        则不关机并在日志里说明原因 —— 宁可多等，也不误关

  - 通知（Pi 独有，默认不勾选）：
      · 勾选后，会话「完成一轮 / 执行失败 / 正在等待工具确认」时弹系统通知
      · 数据来源是 Pi 自己写的 notifications 表（task.completed / task.failed），
        所以是第一时间知道，不靠轮询猜
      · 「等待工具确认」这种会话不会自己继续，退避发送也没用，只有人去点一下才行，
        所以单独提醒，避免以为工具失灵

  - 400 续接规则（仅 Codex，默认开启，报 400 就直接开）：
      · 某个会话返回 "bad response status code 400"（默认 1 次即触发；
        框里可以改大，填 0 = 关闭该功能）后，工具自动在该会话的项目目录下
        用 codex exec 开启新会话，并把原会话的深度链接（codex://threads/<uuid>）
        作为首条消息发送，让新会话继续原任务
      · 触发后原会话停止监控，新会话会被自动加入监控
      · 不需要此功能可取消勾选
      · Pi 侧的对应功能见下一节（机制不同：Pi 还能先压缩上下文，不只是开新会话）

  - 报错自动续接（仅 Pi，默认开启，连续 3 次）：
      · 在哪儿配：Pi 插件面板「会话续跑」里有这三项（启用 / 连续次数 / 方式），
        推荐在这里配一次；GUI 的「报错/400 续接（仅 Pi）」区域是同一个开关，
        打开 GUI 时会自动跟随插件面板的值。
        命令行参数 --context-continue / --context-threshold 显式指定时优先于插件。
      · 另有「真报 400 直接新建会话」（默认开，可单独关掉）：
        会话真报 HTTP 400 时立刻新建会话交接，不等连续次数、也不先压缩 ——
        400 是确定性错误，重发「继续」和压缩上下文都救不了。
        判定用 Pi 日志里的真实 HTTP 状态码，并要求日志时间与该会话最后一个
        回合对得上（容差 5 分钟），所以 503（服务商整体挂掉）不算 400，
        仍走上面的连续次数规则；上下文超限也仍走「先压缩」。
        命令行：--open-new-on-400 on|off。
      · 背景：Pi 会话的 turn 失败时，会在 turns.error_code 里留下错误码。
        Pi 的「400」映射规则（来自 Pi 自身实现）：
            HTTP 400 / 422 → 若消息像「上下文超长」则 CONTEXT_TOO_LARGE，
                             否则 PROVIDER_ERROR
        ⚠ Pi 的 turns 表不存 HTTP 码，所以上面的「连续次数」规则只能按
          PROVIDER_ERROR 近似匹配（它同时也涵盖 5xx）。要精确区分 400 与 503，
          只有读 Pi 自己的日志 —— 「真报 400 直接新建会话」和「全 503 关机」
          都是这么做的（见本节的说明与下一节的判定依据）。
      · 触发：同一会话连续 N 次（默认 3 次）出现触发错误码，二次确认后执行。
        默认触发码：PROVIDER_ERROR,CONTEXT_TOO_LARGE
        「连续」的含义：必须连续出现 N 个新的失败 turn ——
        单次网络抖动不会触发（这是刻意的保护，避免误开一堆新会话）。
      · 两种模式（下拉框选）：
          compact（默认）先调 agent/compact 压缩该会话上下文，再发「继续」；
                         压缩失败或压缩后仍失败，才自动退化为新建会话。
          new            直接在同项目目录下新建会话。
      · 交接内容（新会话的首条消息）自动包含：
          1) 原会话深链 pi-desktop://session/<原id>（Pi 会自动附上原会话
             最近若干条消息的摘录）
          2) 原会话未完成的 todo 清单（session_todo 里 pending/in_progress，
             按 high→medium→low 排序）—— 「还要干什么」最准的来源
          3) 原会话最后一条用户消息（任务原文，防止 todo 不全时丢失目标）
        并明确要求「不要从头重做已经完成的部分」「遇到需要决策的地方自行判断」。
      · 新会话会继承原会话的模型/模式/思考等级（不会退回应用默认模型）
      · 触发后原会话停止监控，新会话自动加入监控（无需手动干预）
      · 新会话必须建在原项目的同一目录下：Pi 只接受同项目的会话引用，
        跨项目的深链会被静默跳过，交接内容就丢了
      · 不需要此功能可取消勾选（等于传 --context-continue off）

  - 运行日志：每行前缀标注来源，如 [Codex] / [Pi]；底部有水平拖动条，
    可勾选「自动换行」看长行

========================================================
【7. 工作原理】

  共同点：
    - 每 10 秒读一次应用本地数据库，判断会话是否真中止
      （Codex 读 ~/.codex/state_5.sqlite + thread_history_1.sqlite
        Pi   读 ~/.pi-desktop/pi.sqlite）
    - 真中止后按退避节奏等待，发送前二次确认（重读库仍中止才发），
      避免误发正在思考/输出的会话
    - 被归档 / 被删除的会话自动停止监控，也不再被自动发「继续」：
        删除看数据库的 deleted_at；归档要看两处 —— Codex 读 threads.archived，
        Pi 读 PI-Desktop 自己的归档表（不在 pi.sqlite 里，见下一节）
    - 监控数不足时自动补入新的活跃会话（自动模式）

  Codex：
    - 沿 codex://threads/<父id> 引用自动跟随中继链（续接后新建的线程）

  Pi：
    - 中止判定 = 会话最后一个 turn 的 status 属于 aborted / error
      （turns.status 取值为 running / complete / completed / error / aborted）
    - 发送 = 往 ~/.pi-desktop/session-keeper/commands/ 写一条指令文件，
      插件读到后调用官方 agent/prompt，并把结果写回 results/
    - 每轮检查插件心跳，插件不在了就停止监控并报错，不会静默失效
    - 动态同步（与 Codex 一致）：会话被删除时自动退出监控；自动模式下监控数不足
      会补入新的活跃会话；Pi 端重命名后显示名自动刷新
    - 可选通知：读 Pi 的 notifications 表，完成/失败/等待确认时弹系统通知
    - 上下文超限续接：读 turns.error_code = CONTEXT_TOO_LARGE，连续 N 次后
      先调 agent/compact 压缩上下文，压不动再用 session/create 新建会话，
      首条消息带 pi-desktop://session/<原id> 深链（由 Pi 自己解析成摘录）

========================================================
【8. 注意】

  - 睡觉时用：确认关机规则按你的意愿开关，取消「模拟运行」，启动后保持 GUI 开着（可最小化）
  - 400 续接会真正启动 codex exec 运行 agent（消耗 token），如不需要请关闭该功能
  - 上下文超限续接也会消耗 token：compact 模式要跑一轮压缩；新建会话会把
    交接消息作为新会话的第一轮。如不需要请取消勾选
  - 工具不会修改你的数据，只读取数据库 + 调用官方接口
    （Codex 用 codex queue/exec；Pi 用插件里的 agent/prompt / agent/compact / session/create）
  - 日志文件：codex_monitor.log / pi_monitor.log 生成在程序同目录
  - Pi 插件需要 desktop.control 权限（即"控制桌面操作"）。
    插件源码就在 Pi插件/local.session-keeper/ 里，可自行审阅：
    它只做四件事——把外部指令转成 agent/prompt、agent/abort、agent/compact、
    session/create 调用，以及写心跳/结果文件。

【9. 只做检测、不发送（安全试跑）】

  勾选界面上的「模拟运行(只检测不发送/不关机)」后启动，
  或命令行：
      python pi_monitor.py --dry-run --once --auto 6      # Pi，看一轮检测结果
      python codex_monitor.py --dry-run --once            # Codex
  这样只打印会做什么，不实际发送、不关机。
